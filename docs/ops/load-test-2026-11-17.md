# Load test and SLOs: 17 November 2026

## SLOs (proposed for launch)
| SLO | Target | Measured at 100 concurrent users (steady state) | Status |
|---|---|---|---|
| Read API latency | p95 < 300 ms | 41 to 60 ms across all read endpoints | ✅ |
| Task creation latency | p95 < 500 ms | 66 ms | ✅ |
| Error rate | < 0.5% (excluding plan limits) | 0 failures in 11,531 requests | ✅ |
| Availability | 99.5% per month | Not measurable here; alerting in `deploy/observability` | ⏳ (production) |
| Task pickup (queued → running) | p95 < 5 s | Workers are woken immediately and poll every 2 s | ⏳ (measure via `agentfirm_queue_oldest_seconds`) |

**SLOs are met in steady state.** The tail (p99 0.5 to 1.2 s) comes from the sign-up burst during ramp-up (next section).

## Setup
**Machine:** one 2-vCPU, 8 GB Firecracker VM running everything:
- one API process, with a pool of 20 + 5 connections;
- one worker, using simulated models with 300 ms latency, so tasks really run;
- PostgreSQL 16;
- the Locust load generator itself.

This is a tighter box than the production server, which also isn't running a load generator.

**Scenario** (`deploy/loadtest/locustfile.py`): each user is a workspace owner.
- They sign up, then list and open tasks, read events, open agents, billing and usage.
- About 1 request in 18 starts a real task.
- 429s from plan limits count as expected.

**Duration:** 4 minutes per level, ramping at 10 users per second. Raw results are in `loadtest-50users.csv` and `loadtest-100users.csv`.

| 100 users | n | p50 | p95 | p99 |
|---|---|---|---|---|
| GET /v1/tasks | 3,792 | 11 | 42 | 550 |
| GET /v1/tasks/{id} | 2,491 | 13 | 49 | 610 |
| GET /v1/tasks/{id}/events | 1,267 | 11 | 41 | 120 |
| GET /v1/agents | 1,235 | 13 | 43 | 910 |
| GET /v1/billing/account | 1,270 | 16 | 60 | 820 |
| GET /v1/usage | 627 | 14 | 56 | 1,200 |
| POST /v1/tasks | 649 | 18 | 66 | 840 |
| POST /v1/auth/register (ramp only) | 100 | 2,300 | 6,500 | 7,400 |

All times in ms. That's about 48 requests per second through one API process, which is about 25% busy.

## Bugs found by load testing (fixed)
1. **Sign-ups with the same workspace name at the same moment returned 500** (`uq_organizations_slug` race). They now retry under a savepoint with a new suffix. A regression test runs 8 concurrent sign-ups.
2. **Argon2 hashing ran on the event loop**, which stalled every request during login and sign-up bursts. It now runs in a thread (`hash_password_async` / `verify_password_async`; argon2-cffi releases the GIL).
3. **The database pool size was hard-coded.** It's now configurable (`AGENTFIRM_DB_POOL_SIZE`, `_MAX_OVERFLOW`, `_POOL_TIMEOUT`).

## Known limits
- **Sign-up bursts are CPU-bound by design.** Argon2 is intentionally expensive: 10 sign-ups per second saturate 2 vCPUs for the burst and raise everyone's p99 meanwhile. Real sign-up rates are far lower, and sign-up and login are rate-limited per IP and email. If needed, move hashing to a bounded process pool or a separate auth worker.
- **One API process** handled 100 users at about 25% busy. Scale by adding API replicas behind Caddy, then raise Postgres `max_connections` (formula in `core/config.py`).
- **Not load-tested:**
  - **SSE fan-out at scale:** each open task view holds a connection and polls the database while it is open. Measure with real browsers on staging.
  - **Live model latency.**
